How an answer is produced — Stozher holds no approver key
Stozher holds no approver private key and has no route that produces an approver's signature, so it cannot manufacture an approval. Sign the request hash with your own owner-only seed file — the one the ceremony wrote, or the copy you keep off this machine. The deployment's own operator seed is at deploy/secrets/operator/operator.seed; a root who keeps theirs elsewhere substitutes their path. 
deploy/bin/stozher-approve <request-hash> --root human:ivan

That is the shipped path and it signs in your own process, which is the property this page exists to preserve. It is one command because the signing and the submitting are both yours to do — not because a button does it for you; nothing here can sign on your behalf.

To sign and submit as separate steps, or to deny with a reason: 
stozher-kernel decide --request <request-hash> --key deploy/secrets/operator/operator.seed \
                      --role 0 --index 0 --approve

stozher-kernel decide --request <request-hash> --key deploy/secrets/operator/operator.seed \
                      --role 0 --index 0 --deny "we don't file public issues for customers"
then paste the object it prints into the form below. --role 0 is the human root key of spec/01 §6; the default, role 1', is an agent subject key and is in no root set.

--deny takes a reason and the reason is not optional. It is what the calling agent is owed (spec/06 §4.1) and what policy tier 3 learns from (docs/design/policy-model.md); a denial without one is refused (gate-denial-without-reason). A gate you can only say yes to is not a gate.

The decision travels into the audit as a gate-decision envelope on the kernel's core stream (spec/06 §5) and into the effect that consumes it as authorization (spec/06 §1.3).
